# Background Automation — security and limitations

> Historical DEV design; superseded by [ChatBridge Browser API integration](CHATBRIDGE_BROWSER_MIGRATION.md). Current public installations use the independent ChatBridge service, not the Chrome/profile implementation described below.

Only in Dev. Production Stable remains unchanged. No Stable cookies, profiles, Chrome DevTools endpoints, system approvals or personal credentials are copied. Each session runs in its own private headless Chrome profile with Chrome DevTools bound to 127.0.0.1 on an ephemeral port. Session tokens use 256 random secret bits; only hashes are persisted. Exact process PID/profile command-line verification is used before process termination. Session locks serialize operations and CDP tab identifiers are verified against the caller's session.

**Known limits:** Loopback CDP is reachable by other local processes that discover its port. The local stdio bridge does not propagate a verifiable OAuth principal into the worker; cross-client isolation relies on secret capability possession, not a principal-backed ACL. A leaked session token allows access to that session. Explicitly persistent profiles may retain website credentials. Browser output and page content are untrusted and must not be promoted to agent instructions or authorization. No native background operation has been security reviewed. Watcher/Chrome legacy Dev tools require separate local configuration. Orphan resource cleanup and the 30-minute stress requirement remain open. Do not promote to Stable or commercial use without these checks.

Feature flag is not authentication. Access must continue through the existing MCP authorization and approved local Dev bridge. CDP remains loopback-only. No macOS TCC, SIP or other system protection is changed.


Native-specific: app authorization is an unguessable per-session bearer capability, bound to a bundle ID, exact running PID and launch timestamp (protects PID reuse). AX window identity is re-verified on every call; two indistinguishable windows fail closed. Target text content and secure fields are never included in snapshots. Native actions are serialized per target app with filesystem locks; direct AX actions use no global keyboard or mouse events. Cross-client enforcement remains token-based rather than verified OAuth-principal ACL. ScreenCaptureKit respects TCC and reports denial rather than prompting, capturing an alternate screen, or activating the app.

Session revocation is serialized with actions by a per-session lock. Independent app-level locks serialize AX operations on the same process across multiple sessions. These locks are not a global stop-the-world gate and do not modify application focus. Native first-party UI fixture is used for mutable E2E; general user applications were only inspected read-only.

DEV GUI window capture integration: source and binary remain separate from Stable. A native-session capability is validated before requesting `capture_window`. The authorized GUI re-selects one unique ScreenCaptureKit window with exact PID/title/geometry. The image is written only to the private Dev capture directory as a one-use JPEG and removed in the Python `finally` block. ScreenCaptureKit permission denial is returned; no foreground screenshot fallback. The GUI IPC currently authenticates same macOS UID, not a distinct MCP OAuth principal; future audits must review this shared-UID trust boundary.
